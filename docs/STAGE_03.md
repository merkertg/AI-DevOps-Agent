# Этап 03. Ограниченный ввод, обезличивание и CLI-отчёт

[← README](../README.md) · [Этап 02](STAGE_02.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md)

## 1. Что теперь можно сделать

На этапе 02 мы создавали `Incident`, `Source` и `Observation` прямо в Python.
Теперь можно передать программе локальный файл с вымышленными данными и получить
полный офлайн-отчёт: временную шкалу, факты, гипотезы, противоречия и сведения
о нехватке данных. Для каждого вывода сохраняется ссылка на исходное наблюдение
в уже обезличенной шкале.

Программа проверяет размер и формат входа, нормализует поля, удаляет явно
поддерживаемые чувствительные шаблоны и только затем готовит отчёт. Если данные
неполные, это остаётся видно даже при успешном завершении команды.

Текущий вход — UTF-8 JSON версии 1. Текст журнала находится в поле `message`.
Отдельного парсера произвольных текстовых логов пока нет. Docker, база, GitPython,
LangGraph, модель и телеметрия на этом этапе не подключаются. Сервер FastAPI
для CLI запускать не требуется, его маршруты не меняются.

## 2. Как связаны файлы

```text
python -m app.cli FIXTURE
           ↓
app/infrastructure/fixtures.py
  ограниченное чтение → строгий JSON → проверка полей
           ↓
app/infrastructure/redaction.py
  поддерживаемые шаблоны → [REDACTED] → ограничение длины
           ↓
app/application/inputs.py: PreparedInput
           ↓
app/application/reporting.py
  investigate() из домена → качество данных → JSON
           ↓
stdout: один документ, либо stderr: безопасная ошибка
```

| Файл или функция | Для чего нужна |
| --- | --- |
| [fixtures.py](../app/infrastructure/fixtures.py), `load_fixture()` | Ограничивает чтение, проверяет схему, создаёт доменные объекты и переводит ошибки в безопасные сообщения |
| `InputLimits` | Хранит конечные ограничения; в тестах можно задать меньшие значения |
| [redaction.py](../app/infrastructure/redaction.py), `redact_text()` | Заменяет поддерживаемые значения маркером и считает замены |
| [inputs.py](../app/application/inputs.py), `PreparedInput` | Передаёт неизменяемый подготовленный вход и сведения о пропусках |
| [reporting.py](../app/application/reporting.py), `build_report()` | Применяет готовый домен и добавляет качество данных, неизвестные обстоятельства и ограничения |
| `render_report()` | Превращает результат в воспроизводимый JSON с явными UTC-датами |
| [cli.py](../app/cli.py), `main()` | Разбирает аргументы и соединяет адаптер с отчётом; возвращает код завершения |
| [fixtures/stage03/](../fixtures/stage03/) | Два вымышленных примера: известные признаки сбоя и неполный сбор |

Предметные правила по-прежнему находятся в `app/domain/`. Они не читают файлы
и не зависят от CLI. Адаптер не содержит нового анализа причин: он переводит
проверенный внешний формат в уже существующие объекты.

У каждой новой функции в коде есть английский docstring с назначением.
Вспомогательные функции адаптера отдельно проверяют объекты, списки, строки,
идентификаторы, время и отдельные записи. Это позволяет одинаково обрабатывать
ошибки всех полей и не печатать исходные значения в диагностике.

## 3. Подготовить окружение

Открой терминал в корне `AIDevOpsAgent`, где лежат `pyproject.toml` и `uv.lock`.
Используются Python 3.12 и uv:

```bash
uv sync --locked
uv run --locked python --version
```

Новых зависимостей для этапа нет: JSON, даты, аргументы и файлы обрабатывает
стандартная библиотека. Локальный `.env` и ключи не нужны. Воспроизводимость
зависимостей и запрет незаметного обновления сохраняются через `--locked`.

## 4. Выполнить первый сценарий

```bash
uv run --locked python -m app.cli fixtures/stage03/connection_failure.json
```

В примере сервис `training-api` сообщает об отказе соединения, затем контейнер
завершается с кодом `1`. Ещё одна запись содержит похожую на команду строку:
она останется текстом и не вызовет действие.

Ожидаемый результат:

- В `timeline` три наблюдения: `obs-refusal`, `obs-exit`, `obs-note`.
- В `facts` два факта; в `hypotheses` две неподтверждённые гипотезы.
- `contradictions` пуст; `data_quality.status` — `declared_complete`.
- Вымышленный email в сообщении заменён на `[REDACTED]`.
- Времена приведены из `+05:00` в UTC, например `2026-10-27T10:00:10+00:00`.
- В `unknowns` сказано, что первопричина не установлена.

`declared_complete` означает «автор фикстуры заявил полноту». Программа
не обращалась к инфраструктуре, чтобы независимо подтвердить эту декларацию.
Даже при полном наборе записей отказ соединения сам по себе не доказывает
причину отказа, а ненулевой код завершения не объясняет причину завершения.

CLI печатает один JSON в стандартный поток вывода (`stdout`). Его можно
сохранить обычным перенаправлением оболочки:

```bash
mkdir -p var
uv run --locked python -m app.cli fixtures/stage03/connection_failure.json > var/stage03-report.json
```

`var/` исключена из Git. Сам CLI не записывает файл и не организует историю
расследований; полноценное хранение относится к этапу 05.

## 5. Как устроен вход

Полный пример находится в
[connection_failure.json](../fixtures/stage03/connection_failure.json).
Минимальный вход с одним наблюдением:

```json
{
  "schema_version": 1,
  "incident": {
    "incident_id": "training-minimal",
    "service": "training-api",
    "starts_at": "2026-10-27T10:00:00Z",
    "ends_at": "2026-10-27T10:05:00Z"
  },
  "sources": [
    {"source_id": "api-log", "service": "training-api", "kind": "application_log"}
  ],
  "observations": [
    {
      "observation_id": "obs-1",
      "source_id": "api-log",
      "event_time": "2026-10-27T10:00:10Z",
      "received_at": "2026-10-27T10:00:12Z",
      "kind": "connection_refused",
      "message": "Fictional dependency connection refused."
    }
  ]
}
```

`schema_version` — целое число `1`. Неизвестные поля и повторные ключи
отклоняются: опечатка не должна молча менять смысл входа. Вместо булева `true`
нельзя передать `1` в декларации полноты; вместо целого кода нельзя передать
`true`, строку или дробь. Дробные и бесконечные JSON-числа здесь не используются.

У наблюдения обязательны идентификатор, ссылка на источник, два времени и вид.
`message` можно не указывать: получится пустая строка. `exit_code` нужен только
для `container_exit`; допустимы целые числа `0..255`. Отказ соединения относится
к `application_log`, завершение контейнера — к `container_state`.

Необязательный объект `collection` содержит:

```json
{"complete": false, "truncated": true, "gaps": ["Fictional missing container state."]}
```

Если `complete` не передан, полнота неизвестна. Пропуски и upstream-обрезание
передаются отдельно, а не выводятся из текста сообщения. Поле `gaps` — список
пояснений от автора входа, его содержимое тоже обезличивается.

## 6. Что нормализуется и что отклоняется

Идентификаторы и имя сервиса очищаются от пробелов по краям. После этого
разрешены ASCII-буквы, цифры, `_`, `-`, `.`, длина от 1 до 64; первый символ —
буква или цифра. Поля с распознаваемым чувствительным шаблоном отклоняются.
Идентификаторы нельзя произвольно заменить маркером: ссылки должны оставаться
однозначными.

У строк времени убираются внешние пробелы. Нужен явный часовой пояс;
корректные моменты приводятся к UTC. Наблюдение должно относиться к сервису
инцидента и попадать временем события в его замкнутый интервал. Время получения
может быть позже конца инцидента, но не раньше самого события.

Виды источника и наблюдения передаются точными строками схемы, например
`application_log` и `connection_refused`. Они преобразуются в доменные `Enum`.
Дубликаты идентификаторов, чужой сервис и неизвестные источники отклоняются
по правилам этапа 02.

Файл должен быть обычным UTF-8 JSON без BOM. Символическая ссылка на месте
самого файла, каталог, FIFO или устройство не принимаются. Открытый файл
проверяется через его дескриптор, а чтение ограничено даже при изменении файла.
Неверная кодировка, повреждённый JSON, недопустимые Unicode-суррогаты и слишком
глубокая вложенность дают безопасную ошибку.

## 7. Ограничения ресурсов

| Что ограничено | Значение по умолчанию | Поведение при превышении |
| --- | --- | --- |
| Размер файла | 1 048 576 байт, то есть 1 MiB | Вход отклоняется до разбора |
| Источники | 32 | Вход отклоняется |
| Наблюдения | 1 000 | Вход отклоняется |
| Интервал инцидента | 24 часа | Вход отклоняется |
| Описания пропусков | 32 | Вход отклоняется |
| Каждое сообщение или пояснение пропуска | 2 048 символов после обезличивания | Текст обрезается с записью метаданных |

Большой список наблюдений не сокращается молча: потеря события могла бы
изменить выводы правил. Для длинного сообщения структурированный вид события
и идентификатор сохраняются, поэтому допускается ограничить только его текст.
Это отражается в `truncated_observation_ids`; число сокращённых пояснений —
в `truncated_gap_count`.

Проверка текстовых шаблонов выполняется до обрезания. Иначе секрет мог бы
пересечь границу и остаться в отчёте частично. Сначала чтение ограничено размером
входа, затем фильтрация, затем ограничение сохранённого текста.

## 8. Какие значения удаляются

Маркер удаления — `[REDACTED]`. Поддерживаются явные шаблоны:

- Присваивания `password`, `passwd`, `token`, `access_token`, `api_key`,
  `api-key`, `apikey`, `secret`, `client_secret` через `:` или `=` без учёта
  регистра. Значения в кавычках могут содержать пробелы; обычные некавыченные
  значения имеют границы токена.
- Учётные значения после `Bearer` из непрерывного набора `[A-Za-z0-9._~+/=-]+`.
- Вся часть пользователя и пароля в URL вида `scheme://user:password@host`.
- Узнаваемые токены с префиксами `sk-`, `sk-proj-`, `ghp_`, `gho_`, `ghu_`,
  `ghs_`, `ghr_`, `github_pat_` и суффиксом не короче восьми символов.
- Поддерживаемые ASCII email-адреса.

Фильтр обрабатывает сообщения и пояснения пропусков. Число замен сохраняется
в `redaction_count`. Оно не равно числу всех возможных секретов и не измеряет
безопасность входа.

Произвольные имена людей, IP-адреса, неизвестные ключи, кодированные значения
и неподдерживаемые форматы могут остаться. Эта реализация не гарантирует,
что любые реальные логи можно безопасно сохранить или отправить модели.
В проекте по-прежнему используются вымышленные данные.

## 9. Проверить неполные данные

```bash
uv run --locked python -m app.cli fixtures/stage03/partial_incident.json
```

Здесь есть один отказ соединения и нет наблюдения о контейнере. Ожидаются один
факт, одна гипотеза и `data_quality.status = "partial"`. Отчёт показывает:

- `declared_complete: false` и `declared_truncated: true`;
- обезличенное пояснение в `gaps`;
- `api-container` в `sources_without_observations`;
- несколько неизвестных обстоятельств в `unknowns`.

Успешный код завершения `0` означает, что отчёт построен. Он не означает,
что данные полные или причина доказана. Пустой набор наблюдений тоже допустим,
но получит `partial` без выдуманных фактов.

Известные пропуски, обрезание, пустая шкала, источник без наблюдений или
противоречие дают `partial` даже при `collection.complete = true`. Если таких
проблем нет, декларация `true` даёт `declared_complete`, а отсутствие
декларации — `unknown`.

## 10. Как проверить доказательство вывода

Открой элемент `facts`, например с кодом `connection_refused`. Внутри будет:

```json
{"evidence": [{"observation_id": "obs-refusal"}]}
```

Найди такой же `observation_id` в `timeline`. Там указаны источник, явный вид
события, время события, время получения и обезличенное сообщение. По этому
же принципу устроены ссылки гипотез и противоречий. Несуществующие ссылки
доменный результат не принимает.

Наличие ссылки проверяет происхождение вывода, а не доказывает произвольное
причинное утверждение. Поэтому `facts`, `hypotheses` и `contradictions`
остаются разными списками.

## 11. Ошибки CLI

| Ситуация | Результат |
| --- | --- |
| Верный вход, в том числе неполный | Код `0`, один JSON в stdout |
| Неизвестный аргумент или не передан файл | Код `2`, статическая подсказка в stderr |
| Файл не читается либо не является обычным файлом | Код `2`, безопасное сообщение |
| Повреждённый JSON, неверный тип или схема | Код `2`, безопасное сообщение |
| Превышен предел байт, записей или интервала | Код `2`, сообщение о лимите |

При ошибке входа stdout пуст. Диагностика не повторяет путь, содержимое файла,
неверное значение или сырое исключение парсера. Это проверяется тестами.
Для справки выполни:

```bash
uv run --locked python -m app.cli --help
```

Повреждённый ввод и превышение лимитов воспроизводятся целевыми тестами:

```bash
uv run --locked pytest tests/test_fixtures.py tests/test_redaction.py tests/test_reporting.py tests/test_cli.py
```

## 12. Как закрыть этап

```bash
uv sync --locked
uv lock --check --offline
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts
uv run --locked pytest
uv run --locked python scripts/check_docs.py
git diff --check
```

Тесты проверяют успешный сценарий, ошибки и лимиты, неполный сбор, инертные
инструкции в сообщениях, удаление поддерживаемых значений, ссылки и фактический
запуск CLI в отдельном процессе. Проверка без `site-packages` подтверждает,
что офлайн-путь использует стандартную библиотеку и не загружает настройки API.

Команды описывают способ проверки. Фактические числа и результат push/CI
находятся в [VERIFICATION.md](VERIFICATION.md),
[verification.json](guide/verification.json) и [журнале](DEVELOPMENT_LOG.md).
После проверок этап коммитится и отправляется в remote; успешный локальный
прогон не заменяет наблюдение удалённого GitHub Actions.

Следующий этап — отдельная Docker-лаборатория и ограниченный сбор наблюдений.
Перед подключением daemon потребуется решить реальную границу его полномочий;
локальное чтение JSON эту задачу не решает.
