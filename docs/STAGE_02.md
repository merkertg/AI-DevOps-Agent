# Этап 02. Инцидент, доказательства и временная шкала

[← README](../README.md) · [Этап 01](STAGE_01.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md)

## 1. Что должно получиться

После этапа 01 приложение умеет отвечать на `/health`. Теперь добавляем основу
расследования: описываем инцидент, передаём вымышленные наблюдения и получаем
воспроизводимую временную шкалу, факты, гипотезы и противоречия.

Учебный пример: сервис `training-api` сообщает об отказе соединения, затем
контейнер завершается с кодом `1`. Программа сохранит оба наблюдения и найдёт
два признака ошибки. Она не сможет доказать, почему соединение отклонено и
почему завершился контейнер. Эти объяснения останутся гипотезами.

На этом этапе данные создаются прямо в Python. Чтение файлов, ограничения
объёма, обезличивание и отдельная CLI-команда относятся к этапу 03. HTTP API
расследований запланирован на этап 08. Для примера не нужны Docker, база,
модель, ключи или сеть.

## 2. Как проходит расследование

```text
Incident: какой сервис и какой интервал расследуем
Source: откуда получено наблюдение
Observation: что и когда зафиксировано
                    ↓
              investigate()
                    ↓
Investigation
  sources          — упорядоченные источники
  timeline         — упорядоченные наблюдения
  facts            — конкретные признаки из наблюдений
  hypotheses       — возможные объяснения
  contradictions   — несовместимые сообщения об одном событии
```

Вся логика находится в [app/domain/](../app/domain/). Она использует стандартную
библиотеку Python и не загружает FastAPI, настройки `.env` или SDK внешних
сервисов. Публичные имена импортируются из `app.domain`.

Модели — `dataclass` с `frozen=True`: после создания поля нельзя присвоить
заново. Результаты представлены кортежами. Это помогает сохранить исходное
доказательство и получить тот же результат при повторном вычислении.
Неизменяемость объектов сама по себе не проверяет достоверность источника.

## 3. Какие объекты нужны

| Объект | Поля | Для чего |
| --- | --- | --- |
| `Incident` | `incident_id`, `service`, `starts_at`, `ends_at` | Устанавливает границы расследования |
| `Source` | `source_id`, `service`, `kind` | Объясняет происхождение данных |
| `Observation` | `observation_id`, `source_id`, `event_time`, `received_at`, `kind`, `message`, `exit_code` | Сохраняет отдельное наблюдение |
| `EvidenceReference` | `observation_id` | Ссылается на наблюдение внутри результата |
| `Fact` | Результат правила и ссылки на наблюдения | Описывает наблюдаемый признак |
| `Hypothesis` | Возможное объяснение и ссылки | Не подменяет предположение доказанным фактом |
| `Contradiction` | Описание конфликта и ссылки | Сохраняет несовместимые свидетельства |
| `Investigation` | Инцидент, источники, шкала и три вида выводов | Собирает результат с проверяемыми ссылками |

У источника два допустимых вида: `SourceKind.APPLICATION_LOG` и
`SourceKind.CONTAINER_STATE`. У наблюдения — `ObservationKind.CONNECTION_REFUSED`,
`ObservationKind.CONTAINER_EXIT` и `ObservationKind.NOTE`.

`Enum` задаёт закрытый набор вариантов. Передаём член перечисления, например
`ObservationKind.CONNECTION_REFUSED`, а не произвольную строку. На этапе 03
отдельный адаптер будет преобразовывать внешний формат в эти объекты.

## 4. Время события и время получения

`event_time` отвечает на вопрос «когда произошло событие?», а `received_at` —
«когда мы получили запись о нём?». Запись может прийти после окончания
расследуемого интервала: это не делает само событие чужим для инцидента.

Все даты должны содержать часовой пояс. Например,
`datetime(2026, 10, 27, 10, 0, tzinfo=UTC)`. Дата без `tzinfo` отклоняется:
из неё нельзя понять, о каком часовом поясе идёт речь. Корректные даты
приводятся к UTC, поэтому `10:00+00:00` и `15:00+05:00` описывают один момент.

Интервал замкнутый: событие ровно в `starts_at` или `ends_at` допустимо.
Начало не может быть позже конца. В текущей модели время получения не может
быть раньше события. Это явное ограничение учебного этапа: обработка
рассогласованных часов реальной инфраструктуры пока не реализована.

Порядок шкалы задаётся явно с разрешением совпадающих времён; порядок
переданного списка не определяет результат. Порядок получения наблюдений
не доказывает порядок их возникновения.

Ключ сортировки: `(event_time, received_at, source_id, observation_id)`.
Источники упорядочиваются по `source_id`. Поэтому при одинаковом времени
события результат всё равно однозначен.

## 5. Запустить вымышленный пример

Перейди в корень репозитория, где находятся `pyproject.toml` и `uv.lock`.
Подготовь окружение:

```bash
uv sync --locked
```

В Bash или zsh выполни весь блок:

```bash
uv run --locked python - <<'PY'
from datetime import UTC, datetime, timedelta

from app.domain import (
    Incident,
    Observation,
    ObservationKind,
    Source,
    SourceKind,
    investigate,
)

start = datetime(2026, 10, 27, 10, 0, tzinfo=UTC)
incident = Incident("demo-02", "training-api", start, start + timedelta(minutes=5))
sources = (
    Source("api-log", "training-api", SourceKind.APPLICATION_LOG),
    Source("api-container", "training-api", SourceKind.CONTAINER_STATE),
)
observations = (
    Observation(
        "obs-refusal", "api-log", start + timedelta(seconds=10),
        start + timedelta(seconds=12), ObservationKind.CONNECTION_REFUSED,
        message="Fictional dependency connection was refused.",
    ),
    Observation(
        "obs-exit", "api-container", start + timedelta(seconds=20),
        start + timedelta(seconds=22), ObservationKind.CONTAINER_EXIT,
        message="Fictional container exit.", exit_code=1,
    ),
)
result = investigate(incident, sources, observations)
print([observation.observation_id for observation in result.timeline])
print("facts:", len(result.facts))
print("hypotheses:", len(result.hypotheses))
print("contradictions:", len(result.contradictions))
print("same after reordering:", result == investigate(
    incident, reversed(sources), reversed(observations)
))
PY
```

Ожидается шкала `['obs-refusal', 'obs-exit']`, два факта, две гипотезы,
ноль противоречий и `same after reordering: True`. Это вызов Python-функции
из терминала; отдельного пользовательского CLI пока нет.

Разберём главное:

1. `Incident(...)` ограничивает расследование одним сервисом и пятью минутами.
2. `Source(...)` задаёт происхождение каждой записи.
3. `Observation(...)` содержит явный вид события и два времени.
4. `investigate(...)` проверяет область, упорядочивает вход и применяет правила.
5. `result.timeline` позволяет найти наблюдение, на которое ссылается вывод.
6. Повторный вызов с обратным порядком проверяет воспроизводимость.

## 6. Как работают правила

Правила читают структурированные поля, а не ищут любые упоминания ошибок
в `message`.

| Вход | Результат |
| --- | --- |
| Явное `CONNECTION_REFUSED` из журнала приложения | Факт отказа соединения и отдельная неподтверждённая гипотеза |
| `CONTAINER_EXIT` с ненулевым целым `exit_code` | Факт ненулевого завершения и отдельная неподтверждённая гипотеза |
| `CONTAINER_EXIT` с кодом `0` | Наблюдение и факт штатного завершения сохраняются; гипотеза ошибки не создаётся |
| `NOTE` с текстом об ошибке или командой | Текст остаётся данными, правило ошибки не срабатывает |
| Разные коды завершения у одного источника в один момент | Оба наблюдения сохраняются, появляется противоречие; гипотеза для спорной группы подавляется |

Например, коды `0` и `1` в один момент нельзя молча заменить одним «правильным»
кодом. Программа показывает конфликт. Сам факт того, что источник сообщил
ненулевой код, остаётся связан с конкретной записью, но его нельзя выдавать за
бесспорное описание произошедшего.

Источник состояния в этой модели должен обозначать одну наблюдаемую сущность
(например, один контейнер). Два контейнера получают разные `source_id`.
Противоречия между независимыми источниками и сложные причинные цепочки эти
простые правила не устанавливают.

## 7. Почему ссылки проверяются отдельно

Каждый факт, гипотеза и противоречие содержит `EvidenceReference`. Ссылка
должна указывать на существующее `observation_id` в шкале того же расследования.
Конструктор результата отклоняет неизвестную ссылку.

Это проверка наличия доказательства. Она не означает, что произвольное
утверждение внешней модели логически следует из указанной записи. Настоящая
LLM ещё не подключена; проверка её структурированных ответов появится вместе
с соответствующим поведением.

## 8. Ошибки и границы

| Ситуация | Что происходит и как исправить |
| --- | --- |
| Дата без часового пояса | `ValueError`; явно укажи `tzinfo` |
| Конец раньше начала или получение раньше события | `ValueError`; проверь времена и их происхождение |
| Событие раньше начала или позже конца инцидента | `ValueError`; исправь область или вход, запись не отбрасывается молча |
| Источник другого сервиса | `ValueError`; это отдельное расследование |
| Неизвестный `source_id` | `ValueError`; передай соответствующий источник |
| Повторный идентификатор источника или наблюдения | `ValueError`; идентификаторы должны быть однозначны |
| Неизвестная ссылка доказательства | `ValueError`; ссылка должна разрешаться в текущей шкале |
| Код завершения отсутствует, вне `0..255` либо передан `True` | `ValueError`; нужен целый код из допустимого диапазона |
| Вид наблюдения не подходит источнику | `ValueError`; отказ соединения относится к журналу приложения, завершение — к состоянию контейнера |
| Пустой список наблюдений | Допустимый пустой результат без выдуманных выводов |

Сообщения журналов могут содержать инструкции вроде «игнорируй правила».
Они сохраняются как строки. В домене нет исполнения команд, чтения файлов,
доступа к Docker или отправки запросов. Обезличивания пока тоже нет, поэтому
пример и тесты используют только вымышленные данные.

## 9. Что проверяют тесты

Запусти целевой и полный набор:

```bash
uv run --locked pytest tests/test_domain.py
uv run --locked pytest
```

Проверяются корректные и ошибочные модели, смещения часовых поясов, границы
интервала, одинаковые времена, перестановки входа, ссылки, конфликты,
неизменяемость и инертность текста. Полный набор дополнительно проверяет
контракт `/health` и настройки из этапа 01.

Все обязательные команды:

```bash
uv sync --locked
uv lock --check --offline
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts
uv run --locked pytest
uv run --locked python scripts/check_docs.py
git diff --check
```

Назначение проверок объяснено в [инструкции](instructions/testing.md).
Фактические результаты находятся в [отчёте](VERIFICATION.md) и
[verification.json](guide/verification.json). Успешный локальный тест,
отправленный коммит и успешный запуск GitHub Actions фиксируются отдельно.
