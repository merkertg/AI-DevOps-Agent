# Этап 05. Сохранённые расследования и история деплоев

[← README](../README.md) · [Этап 04](STAGE_04.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md)

## 1. Что должно получиться

Раньше CLI печатал отчёт, который исчезал вместе с закрытым терминалом, если
его отдельно не сохранить. Теперь расследование можно записать в локальный
SQLite-файл, открыть следующим процессом и проверить, что сохранённый вход
даёт тот же отчёт.

Второе дополнение — история деплоев одного вымышленного Git-репозитория.
Она добавляет на шкалу явную запись выпуска и позволяет заметить, что после
неё появился признак сбоя. Порядок событий не доказывает причину: программа
сохранит это ограничение в гипотезе и отчёте.

Для полного учебного сценария нужны Python 3.12, uv и установленный `git`.
Сервер базы, Docker и модель не нужны. SQLite входит в стандартную библиотеку,
GitPython добавлен в зависимости и закреплён в `uv.lock`. Обычный запуск
без `--repository` не импортирует GitPython и сохраняет прежний офлайн-путь.

## 2. Как проходит обработка

```text
JSON-фикстура или ограниченный сбор Docker
                     ↓
                PreparedInput
                     ↓
необязательная история: GitPython → разрешённые annotated tags
                     ↓
           наблюдения о деплоях + пропуски
                     ↓
       доменные факты, гипотезы и шкала
                     ↓
без --store: JSON-отчёт в stdout
с --store: канонический вход + исходный отчёт + версии + SHA-256
                     ↓
                  SQLite
                     ↓
       новый процесс: list / show / verify
```

Выбор хранения записан в [ADR 0003](adr/0003-immutable-investigation-records.md),
а формат и границы чтения истории — в
[ADR 0004](adr/0004-recorded-lab-deployments.md).

## 4. Подготовить окружение и лабораторию

Выполняй команды из корня `AIDevOpsAgent`:

```bash
uv sync --locked
git --version
uv run --locked python lab/stage05/make_history.py create var/stage05/training-api
```

Последняя команда создаёт новый каталог с тремя вымышленными коммитами и двумя
аннотированными тегами деплоя. Путь назначения не должен существовать.
Скрипт не продолжает работу в произвольном существующем репозитории и не
перезаписывает каталог при повторном `create`. Для нового прогона выбери новый
путь и укажи его в последующих командах.

Это **подготовка лаборатории разработчиком**: скрипт создаёт файлы, коммиты
и теги. Сам исследователь этот скрипт не вызывает и не меняет исследуемый Git.
Каталог `var/` исключён из Git; учебная история не становится вложенным
репозиторием в коммите основного проекта.

В лаборатории последняя ревизия меняет порт зависимости на `5432`.
Её commit time — `2026-10-29T09:40:00+00:00`; отдельно зафиксированный деплой —
`2026-10-29T10:20:00+00:00`. Разные времена намеренны: коммит может появиться
раньше выпуска.

## 5. Получить отчёт с историей

```bash
uv run --locked python -m app.cli fixtures/stage05/after_deployment.json --repository var/stage05/training-api
```

Фикстура задаёт инцидент `training-after-deployment`, сервис `training-api`
и интервал `10:00–10:30 UTC` 29 октября 2026 года. В ней есть три наблюдения:
запуск, отказ соединения в `10:25:00` и завершение контейнера с кодом `3`.

История добавит деплой в `10:20:00` и служебное наблюдение с итогом чтения тегов.
Первый деплой 27 октября находится вне окна и в шкалу не попадёт.
Для неизменённой лаборатории ожидаются пять наблюдений, три факта и три
гипотезы. Одна из гипотез имеет код `deployment_preceded_failure`: она ссылается
на деплой и следующий признак сбоя, явно указывая, что это не доказанная причина.

Источник истории называется `training-api-lab-deployments`, его вид —
`deployment_history`. Запись деплоя имеет вид `deployment`. В тексте наблюдения
сохраняются разрешённое имя репозитория, тег, SHA объекта тега, SHA ревизии,
время коммита и время записи тега; краткое сообщение коммита обезличивается
и ограничивается по длине.

## 6. Почему commit time не становится временем деплоя

В аннотированном теге `deploy/lab/0002` лежит сообщение такого формата:

```json
{
  "record": "ai-devops-agent.deployment",
  "version": 1,
  "service": "training-api",
  "environment": "lab",
  "deployed_at": "2026-10-29T10:20:00+00:00"
}
```

Схема принимает ровно эти поля. Время деплоя берётся из `deployed_at` с явным
часовым поясом; время получения наблюдения — из времени записи тега.
Сообщение должно называть разрешённые сервис и среду. Деплой не может быть
раньше соответствующего коммита или позже записи тега. Неверная запись
пропускается с объяснением в `gaps`.

Обычный lightweight tag не содержит нужной записи. Произвольный текст вроде
«последний коммит уже выпущен» тоже не становится деплоем. Commit summary —
данные для контекста, а не инструкция и не источник времени выпуска.

Даже правильная запись — утверждение автора лаборатории. Она не доказывает,
что эта ревизия действительно исполнялась на сервере. Здесь нет подписи,
сверки с реальным deployment-сервисом или проверки работающего контейнера
по Git SHA.

## 7. Сохранить расследование

```bash
uv run --locked python -m app.cli fixtures/stage05/after_deployment.json --repository var/stage05/training-api --store var/stage05/investigations.sqlite3 > var/stage05/receipt.json
```

Теперь stdout содержит квитанцию, а не полный отчёт. В ней есть:

- `investigation_id` вида `inv-` и 24 шестнадцатеричных символа;
- `created: true` для новой записи;
- `incident_id`, `origin`, `data_quality`, `stored_at`, `app_version`;
- полный `input_sha256` и `report_sha256`.

В SQLite сохраняются подготовленный вход, первоначальный отчёт, их версии
и хеши. Исходный файл, сырые Docker-ответы и локальный путь репозитория
в снимок не копируются. Сохраняются уже нормализованные наблюдения, источники,
обезличенный текст и метаданные качества.

Для того же входа повтори команду. Получится `created: false`, тот же ID
и первоначальное время сохранения. Идентичность определяется каноническим
подготовленным входом: другое оформление исходного JSON само по себе не
создаёт новую запись. Новое время запуска тоже не меняет его идентичность.
Изменившиеся наблюдения или сведения об истории дают другой снимок и ID.

Если `--store` не передан, приложение продолжает печатать обычный отчёт.
`python -m app.collect` тоже принимает `--repository` и `--store`, но для
настоящего сбора ему нужен Docker по правилам этапа 04. Текущий сценарий
хранения воспроизводится на фикстуре без Docker.

## 8. Прочитать запись новым процессом

Посмотри список:

```bash
uv run --locked python -m app.investigations list --store var/stage05/investigations.sqlite3
```

Он покажет общее число записей `total` и до 20 сводок, начиная с нового времени
сохранения. Число можно задать через `--limit`, допустим диапазон `1..500`.
Список не загружает полные отчёты.

Чтобы следующие команды можно было выполнить целиком в Bash или zsh, прочитай
ID из созданной квитанции в переменную `id`:

```bash
id=$(uv run --locked python -c 'import json; from pathlib import Path; print(json.loads(Path("var/stage05/receipt.json").read_text())["investigation_id"])')
uv run --locked python -m app.investigations show "$id" --store var/stage05/investigations.sqlite3
uv run --locked python -m app.investigations verify "$id" --store var/stage05/investigations.sqlite3
```

`show` выдаёт исходный JSON отчёта после проверки его хешей и ID. Он не читает
фикстуру и не собирает Git или Docker заново. Даже если в лаборатории появились
новые данные, эта запись останется прежней.

`list`, `show` и `verify` открывают существующий файл в режиме только чтения.
Если файла нет, они не создают пустую базу вместо ошибки.

## 9. Что именно проверяет verify

При успешной проверке ответ содержит `status: "verified"` и результаты:

| Проверка | Что означает |
| --- | --- |
| `input_sha256` | Байты сохранённого входа совпали с его хешем |
| `report_sha256` | Байты сохранённого отчёта совпали с его хешем |
| `investigation_id` | ID соответствует префиксу хеша входа |
| `input_decodes` | Снимок читается по поддерживаемой схеме и канонической форме |
| `metadata_matches` | Версии и связанные поля сводки согласованы с документами |
| `report_reproduced` | Текущий код построил из сохранённого входа точно такой же отчёт |

Хеш — отпечаток байтов, а не доказательство истинности наблюдения. Пользователь
с доступом к SQLite-файлу способен заменить и документ, и его хеш. Триггеры
запрещают обычные SQL update/delete/replace, но владелец файла может убрать
их или заменить сам файл. Подписи и защищённое внешнее хранение не добавлены.

Перестроение выполняется **текущим кодом**. Если в будущем изменится правило,
текст или формат отчёта, проверка старой записи может дать `failed`. Исходный
отчёт при этом не перезаписывается. Для новой интерпретации нужно отдельно
продумать версионирование правил, а не незаметно менять старое расследование.

## 10. Увидеть новый деплой без изменения старого отчёта

Разработчик может добавить следующий учебный тег:

```bash
uv run --locked python lab/stage05/make_history.py deploy var/stage05/training-api --at 2026-10-29T10:26:00+00:00
uv run --locked python -m app.cli fixtures/stage05/after_deployment.json --repository var/stage05/training-api --store var/stage05/investigations.sqlite3
uv run --locked python -m app.investigations show "$id" --store var/stage05/investigations.sqlite3
```

Новая запись тега меняет собранный вход, поэтому появится новое расследование.
Команда `show` со старым ID по-прежнему читает старый отчёт. Сам исследователь
не создаёт этот тег: запись выполнена отдельной командой подготовки лаборатории.

## 11. Ограничения и недоступная история

| Ограничение | Значение по умолчанию |
| --- | --- |
| Репозиторий | Только кодовая идентичность `training-api-lab` с закреплённым корневым коммитом |
| Сервис / среда / теги | `training-api` / `lab` / `deploy/lab/` |
| Число читаемых тегов | Первые 100 по имени |
| Размер объекта тега | До 4 096 байт |
| Размер объекта коммита | До 65 536 байт |
| Текст наблюдения истории | До 2 048 символов после обезличивания |
| Каждый сохранённый документ | До 8 MiB |
| Сводки в одном списке | От 1 до 500, по умолчанию 20 |

Большой, повреждённый, неподходящий или лишний тег даёт видимый пропуск.
Доступные корректные записи продолжают участвовать в расследовании.
Недоступный путь или Git даёт gap о неизвестной истории и `partial`.
Репозиторий вне списка или другой сервис отклоняется с кодом `2`.

Проверка закреплённого корневого объекта — соглашение об идентичности лаборатории,
а не аутентификация и не доказательство происхождения всех ревизий. Чтение
предназначено для локальной учебной среды. Его ограничения объектов не являются
жёстким ограничением всей длительности и всех внутренних обходов ссылок GitPython.
Это не песочница для произвольного враждебного репозитория.

Git-переменные, перенаправляющие доступ к другому репозиторию или объектам,
отклоняются. Linked worktrees, alternate object directories и reftable не
поддерживаются. Сборщик не вызывает checkout/reset/pull/fetch/commit/push
и не исполняет содержимое сообщений. Он читает теги и объекты.

В хранилище нет миграций, серверной базы, API доступа, очистки истории или
backup/restore-команд. Файл содержит локальные данные и должен оставаться вне
Git. Фильтр по-прежнему удаляет только документированные виды чувствительных
значений; используются вымышленные наблюдения.

## 12. Ошибки и проверка этапа

| Ситуация | Код завершения |
| --- | --- |
| Отчёт, квитанция, список или показ записи построены | `0` |
| `verify` подтвердил все проверки | `0` |
| `verify` обнаружил несогласованность или невоспроизводимость | `1` |
| Ошибка аргументов, области, SQLite или отсутствующий ID | `2` |

Неизвестный ID не создаёт новую запись. Существующий произвольный SQLite-файл
не принимается за поддерживаемое хранилище. Диагностика исследовательских CLI
не повторяет сырые значения и локальные пути.

```bash
uv run --locked pytest tests/test_records.py tests/test_snapshots.py tests/test_sqlite_store.py tests/test_git_history.py tests/test_deployments.py tests/test_domain_deployments.py tests/test_investigations_cli.py
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy app tests scripts
uv run --locked pytest
uv run --locked python scripts/check_docs.py
uv lock --check --offline
git diff --check
```

Тесты используют временные SQLite-файлы и отдельные копии вымышленного
репозитория. Они не требуют Docker, внешних сервисов или настоящих credentials.
Фактические результаты записываются в [отчёте](VERIFICATION.md),
[verification.json](guide/verification.json) и [журнале](DEVELOPMENT_LOG.md).
Push и результат GitHub Actions проверяются отдельно для конкретного коммита.

Следующий этап — ограниченное расследование через LangGraph поверх готовых
наблюдений и сохранённых материалов. Модель и инструменты изменения систем
в текущий этап не входят.
