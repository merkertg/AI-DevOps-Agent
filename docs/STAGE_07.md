# Этап 07. Телеметрия: метрики, трассировки и их связь с логами

[← README](../README.md) · [Этап 06](STAGE_06.md) · [Дорожная карта](ROADMAP.md) · [Проверки](VERIFICATION.md)

## 1. Что должно получиться

До этого этапа расследование опиралось на логи, состояние контейнера и записи
о деплоях. Теперь к ним добавляются два новых вида данных:

- **метрики** из Prometheus — числа, которые сервис отдаёт регулярно, например
  счётчик неудачных подключений;
- **трассировки** OpenTelemetry — записи об отдельных операциях (spans)
  с идентификатором запроса `trace_id`.

Программа связывает эти данные с логами по сервису, времени и `trace_id`.
Если запись в логе и span имеют один и тот же `trace_id`, появляется факт
`same_trace`: два источника описывают один и тот же запрос.

Важно и то, чего программа **не** делает: совпадение по времени она не выдаёт
за доказанную причину, а недостающие данные явно показывает в отчёте —
отсутствие `trace_id`, задержку или прекращение сбора метрик, расхождение часов
и недоступный источник.

Для офлайн-примера нужны только Python 3.12 и uv. Для живой лаборатории —
ещё Docker Engine 25.0+ и загрузка трёх закреплённых образов.

## 2. Как данные проходят через программу

```text
лог (JSON-строка с trace_id) ─┐
                              ├─→ PreparedInput ─→ факты, гипотезы, пропуски ─→ отчёт
метрики: Prometheus ──────────┤     ↑
  (только разрешённые запросы) │     └ add_telemetry_evidence(): same_trace,
трассировки: файл OTLP ───────┘       нет trace_id, нет трассировки, сдвиг часов
```

Решение о границах записано в [ADR 0006](adr/0006-allowlisted-telemetry.md).

## 4. Офлайн-пример

```bash
uv sync --locked
uv run --locked python -m app.cli fixtures/stage07/incident.json --metrics-file fixtures/stage07/metrics.json --traces fixtures/stage07/traces.jsonl
```

Фикстура описывает вымышленный инцидент 29 октября 2026 года с 11:00 до
11:10 UTC. В логе три отказа соединения с trace ID, затем контейнер
завершается с кодом `3`. В файле трассировок есть три span с ошибкой под теми
же trace ID. Записанные ответы Prometheus показывают рост счётчика ошибок и
недоступность цели после завершения процесса.

В отчёте ожидаются 13 наблюдений, три факта `same_trace`, три
`trace_error_recorded`, два `metric_threshold_exceeded` и статус `partial`.
Единственный пропуск сообщает, что метрика `dependency_failures` перестала
поступать за 525 секунд до конца окна. Это честное отражение данных: процесс
завершился, и Prometheus больше нечего было собирать.

## 5. Какие метрики можно запросить

| Имя | PromQL | Сигнал, когда |
| --- | --- | --- |
| `dependency_failures` | `increase(training_api_dependency_failures_total{job="training-api"}[1m])` | значение `> 0` |
| `target_down` | `1 - up{job="training-api"}` | значение `> 0` |

Текст запросов задан в коде. Его нельзя передать через аргументы, получить из
лога или от агента: клиент отклоняет любое другое выражение до подключения.
Адрес Prometheus — только `http://127.0.0.1:порт`, `localhost` или `[::1]`,
без пути, параметров и учётных данных.

Каждый подъём выше порога становится одним `metric_signal`. Для каждого
запроса добавляется заметка-сводка: сколько точек, с какого по какое время
и какой максимум.

## 6. Как читаются трассировки

OpenTelemetry Collector в лаборатории получает spans по OTLP/HTTP и пишет их
в файл JSON lines. Программа читает этот файл с ограничениями:

- обычный файл, не символическая ссылка, UTF-8, не больше 4 MiB;
- не больше 10 000 строк и 2 000 spans;
- только spans сервиса `training-api`;
- неверные строки и spans пропускаются и считаются в пропусках.

В окне инцидента каждый span со статусом ошибки становится `trace_error`
с trace ID. Все spans окна запоминаются для проверки времени.

## 7. Что проверяется при объединении

| Проверка | Что появляется в отчёте |
| --- | --- |
| У лога и span один trace ID | Факт `same_trace` со ссылками на оба наблюдения |
| Отказ соединения в логе без trace ID | Пропуск со списком таких наблюдений |
| Лог ссылается на trace ID, которого нет в экспорте | Пропуск: spans могли задержаться, быть отброшены или потеряны |
| Время лога дальше 1 секунды от его spans | Пропуск: часы лога и трассировки могут расходиться |
| Последняя точка метрики старше 60 секунд к концу окна | Пропуск: сбор задержался или цель перестала отвечать |
| Нет данных, несколько рядов, NaN, Prometheus недоступен | Пропуск по метрике или один общий пропуск |
| Экспорт не найден, слишком большой или не UTF-8 | Пропуск: трассировки неизвестны |

Любой пропуск делает статус отчёта `partial`. В ограничениях отчёта сказано,
что телеметрия показывает симптомы, а совпадение по времени — корреляция,
а не причина.

## 8. Совпадение по времени — не причина

Правило о деплое из этапа 05 связывает деплой только со сбоем, который
произошёл **строго позже**. Теперь сбоем считаются и `metric_signal`,
и `trace_error`. Если метрика выросла в ту же секунду, что и деплой, правило
их не связывает. Даже связанная пара остаётся гипотезой с оговоркой, что
порядок событий не доказывает причину.

Факт `same_trace` тоже осторожен: он утверждает, что записи описывают один
запрос, и прямо говорит, что согласие источников не объясняет причину сбоя.

## 9. Живая лаборатория

```bash
mkdir -p var/stage07/telemetry
docker compose -f lab/stage07/compose.yaml up -d
docker wait aidevops-lab07-api
uv run --locked python -m app.collect --lab stage07 --minutes 10 --prometheus http://127.0.0.1:19090 --traces var/stage07/telemetry/traces.jsonl
docker compose -f lab/stage07/compose.yaml down -v
```

В лаборатории три контейнера:

- `aidevops-lab07-api` — вымышленный сервис на стандартной библиотеке Python.
  Шесть раз с интервалом 5 секунд пытается подключиться к закрытому порту,
  пишет JSON-строку с `trace_id`, увеличивает счётчик и отправляет span,
  затем завершается с кодом `3`;
- `aidevops-lab07-otel` — OpenTelemetry Collector `0.161.0`, пишет spans
  в `var/stage07/telemetry/traces.jsonl`;
- `aidevops-lab07-prometheus` — Prometheus `v3.15.0`, опрашивает сервис каждые
  5 секунд и доступен только на `127.0.0.1:19090`.

Контейнеры общаются через внутреннюю сеть без выхода наружу. Docker socket
не монтируется. API администрирования Prometheus не включён. Сборщик Docker
читает только контейнер `aidevops-lab07-api` с меткой
`ai-devops-agent.lab=stage07` — его нужно выбрать параметром `--lab stage07`.

На macOS Docker Desktop может не иметь доступа к папке `~/Desktop` из-за
настроек конфиденциальности. Тогда `up` завершится ошибкой
`operation not permitted`. Разреши доступ в системных настройках сам или
запусти копию лаборатории из другой папки, сохранив относительные пути.

## 10. Сохранение и агент

Параметры телеметрии работают вместе с `--repository` и `--store`. Trace ID
и список прочитанной телеметрии попадают в сохранённый вход, поэтому `verify`
воспроизводит отчёт. Для расследований без телеметрии эти поля не пишутся,
и прежние записи этапов 05–06 по-прежнему проходят `verify`.

Агент этапа 06 видит новые факты через те же инструменты. Офлайн-провайдер
добавляет гипотезу о согласии логов и трассировок со ссылками на факты
`same_trace`. В каталоге проверок появилась `review_trace` — посмотреть
трассировку ошибочного span.

## 11. Ограничения

- Допуск сдвига часов — 1 секунда. Время лога Docker — время получения строки
  демоном; при большой задержке сдвиг может как скрыться, так и появиться.
- Устаревание метрики измеряется в момент сбора: остановленный процесс
  и задержанный опрос выглядят одинаково.
- Файл экспорта не аутентифицирован: программа доверяет тому, что разработчик
  указал выход своей лаборатории.
- Метрики и трассировки — симптомы. Они не доказывают первопричину.
